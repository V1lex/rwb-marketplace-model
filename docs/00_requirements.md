# Разбор требований

Источники: репозиторий организаторов (`docs/task/handout.md`, `docs/task/tasks.md`),
презентация кейса (RWB, «Модель маркетплейса: от корзины до выкупа»), вступительное
слово эксперта WB и ведущего (расшифровки голосовых).

## 1. Постановка

Мы — архитекторы данных маркетплейса Capibara (данные Olist, 09.2016–10.2018).
Восемь «грязных» выгрузок лежат в схеме `raw` (все колонки `text`, 550 759 строк).
Нужно спроектировать модель, на которую аналитики смогут опереться: одинаковые
цифры для одинаковых вопросов, без пересборки отчёта каждый раз заново.

Жёсткие правила из раздаточного материала:

| Правило | Как выполняем |
|---|---|
| `raw` не меняем | Только читаем. Скрипты организаторов перенесены без изменений |
| Модель в `core`, наполняется из `raw` | `01_model/*.sql`, собирается одной командой `make build` |
| Ответы считаются из модели, не из `raw` | Все запросы в `02_answers/` обращаются только к `core` и `mart` |
| Скрипт собирает модель с нуля на чистой базе | `make all` = окружение + сборка + проверки + ответы; CI повторяет это на каждом коммите |
| Решения придётся объяснить | Комментарии `COMMENT ON` на каждой таблице и колонке, записка, журнал ИИ |

## 4. Слои (как сказал эксперт: raw → ODS → модель → витрины)

```
raw   (организаторы)  как пришло, text
 └─ stg   (ODS)       представления: типизация, trim/nullif, нормализация справочных значений
     └─ core (DDS)    звезда: измерения + факты, ключи, ограничения, COMMENT
         └─ mart      семантический слой: каталог метрик, витрины, ответы
dq                    сверки raw ↔ core и бизнес-инварианты, журнал прогонов
```

## 5. Подводные камни данных, которые обязана учесть модель

Всё проверено на загруженных данных, подробности и SQL — в `docs/01_data_profile.md`.

* `customer_id` уникален для каждого заказа; человек — `customer_unique_id` (96 096).
* `order_item_id` — номер единицы товара в заказе: зерно позиции = одна единица.
* `review_id` не уникален (789 отзывов на несколько заказов, 547 заказов с несколькими отзывами).
* В ноябре 2016 заказов нет совсем: нужен календарь, иначе месяц выпадет.
* 610 товаров без категории, у 2 категорий нет перевода: член «без категории» и запасной перевод.
* 775 заказов без позиций, 1 заказ без платежей, 366 заказов, где оплата ≠ товары + доставка.
* Хронология: 166 заказов переданы в доставку раньше оформления, 23 вручены раньше передачи.
* 8 `delivered` без даты вручения, 6 `canceled` с датой вручения.
* Города продавцов: `sao paulo - sp`, `sbc/sp`, email и цифры вместо города.
* Таймстемпы без часового пояса (местное время Сан-Паулу).
* `geolocation` в выдачу не входит (8 файлов = 550 759 строк без него), в модели не используется.

## 6. Блок Б: к чему готовимся

Через половину хакатона придут ещё 5 вопросов и «вброс». Модель не оптимизируем
под первую пятёрку. Прогоняем её на расширенном списке вероятных вопросов
(платежи, логистика и SLA, отзывы, когорты, концентрация продавцов) и вбросов
(комиссии, смена правила выручки, штрафы, дозагрузка, история цен, возвраты,
валюты, сверка оплат, доразметка категорий). Готовность фиксируется
в `02_answers/block_b_readiness/`: на каждый сценарий есть запрос к модели,
который отрабатывает без переделки `core`.

## 7. Прочтение под Wildberries

Эксперт WB просил думать шире одной покупки. Термины Capibara переводим на язык WB:

| Capibara (Olist) | WB |
|---|---|
| `delivered` | выкуп; выручка признаётся по выкупленным заказам |
| `canceled`, `unavailable` | отмена или невыкуп, потерянный спрос |
| `shipping_limit_date` | SLA отгрузки продавца (FBS), основа для штрафов |
| `order_estimated_delivery_date` | обещанный срок в карточке, основа для доверия покупателя |
| `freight_value` | логистика, которую платит покупатель |
| `payment_installments`, `voucher` | рассрочка («Сплит») и баллы/промокоды |
| отзывы | рейтинг продавца и карточки, сигнал для ранжирования |

## 8. Порядок работы (каждый шаг — отдельный коммит)

4. Ответы блока А с автопроверкой контрольных цифр.
5. Готовность к блоку Б: вероятные вопросы и вбросы.
6. Записка о решениях.
7. Концепция дашборда.
8. Стратегия развития.
9. Журнал использования ИИ.
10. CI: сборка и проверки на чистой базе.
